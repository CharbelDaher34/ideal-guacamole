Cash-flow forecasting · How it works

Digital Cash Management Forecast

For every business client, we forecast the net cash flow (money in minus money out) of each of the next 3 months, per category and in total, as a low value (P10), an expected value (EV) and a high value (P90). This project builds everything around the model; the model itself is a placeholder until the data scientist's models replace it.

7 November 2026 · Draft for the squad and the tech lead

1The whole journey

Daily postings become each client's money in and money out per day and category. A forecaster reads that history and returns, per client and category (and in total), P10, EV and P90 for the next 3 months.

flowchart LR
  A[Statement entries: EDW.FCT_STATEMENT_ENTRY] --> C[daily_flows: money in and out per client, day and category]
  K[Clients: EDW.DIM_CUSTOMER] --> CL[clients: business clients]
  C --> F[Forecaster: placeholder now, data scientist's model later]
  CL --> F
  F --> I[Forecast: per client, category and TOTAL, 1-3 months ahead, P10 / EV / P90]

No schedule of future payments is used: the warehouse tables give none, so the forecast comes from each client's history.

2Who builds what

This project (around the model)

  • Getting the data: read the 2 warehouse tables, read-only, and turn them into daily_flows and clients, the format every model works on.
  • The inference pipeline: forecast every active client with the production model, archive and log each run.
  • The promotion pipeline: test every new model the same way, and promote it only if it passes the rules (project variables).

The data scientist (the model)

  • Explores the data and tries models in the lab, without touching production.
  • Puts a model in production by writing a forecaster: a small class with fit and predict (section 4).
  • Small models only (for example gradient boosting), no deep learning.

3The data

The project reads 2 tables of the bank's warehouse, read-only, through the database connection (Oracle) or as CSV files in a landing folder. Nothing is created or written in the warehouse: the only query is a read-only SELECT with a date filter. Until the connection is set, a simulator writes sample tables shaped like the bank's.

TableWhat the project readsWhat it becomes, in Dataiku
EDW.DIM_CUSTOMERThe clients: CIF, customer type, line of business, legal entity, ID type, segment, sector, industry, city, status. Personal fields are never read.clients: the business clients (every line of business but retail, plus retail clients with a commercial registration: businesses owned by one person)
EDW.FCT_STATEMENT_ENTRYThe daily postings: CIF, value date, credit or debit, amount in SAR, transaction type, reference, reversal markerdaily_flows: one row per client, day and category with money in and money out, over each client's whole history, without reversed postings and transfers between the client's own accounts
  • Categories come from each posting's transaction type (TRNS_TYP), through one list in warehouse.py; a type not in the list goes to OTHER. The list is a mock for now (customer receipts, salaries, rent, suppliers, financing, government, utilities, cards, fees, other): at the bank it is replaced by the real codes, and nothing else changes.
  • The client number (CSTMR_CIF) ties the 2 tables together.
  • Each client's whole history is kept: no cut at 2 or 5 years.
  • Only the new days are read. The first run reads the whole history once. After that, each run reads only the postings after the last day already in daily_flows (WHERE VAL_DT >= …) and adds them. staging_log records each read.
  • Full rebuild, a scenario run by hand, empties daily_flows and reads the whole history again: for example after a reversal cancels a posting from a day already staged, which a nightly read can't take out.

4The forecaster: the plug between the data and the model

A forecaster is a small class. Any model that follows it can be tested, tracked, promoted and run every night without changing the rest of the project.

PartWhat it is
fit(daily, clients, cutoff)Learns from the daily flows known at the end of the cut-off month, and the clients
predict(daily, clients, cutoff)Returns one row per client, category (and TOTAL: all its categories together) and months ahead (1, 2, 3): P10, EV and P90 of that month's net cash flow, in SAR
name, paramsIts name (the project variable forecaster selects it) and its settings (recorded with each model)

The placeholder, quantile_boosting: 3 small models (scikit-learn gradient boosting), one for the EV, one for P10, one for P90, all on the last 12 months of each client and category. Each of the 3 serves every category and TOTAL, with the category as an input, rather than one set of models per category: a category with little data learns from the others, and there are 3 models to track and promote instead of 3 per category. The 3 are saved and promoted together, in one version of the saved model. Its job is to let the whole pipeline run end to end with real models; the data scientist replaces it.

The lab compares it with one set of 3 models per category (quantile_boosting_by_category) and with recent_average (no machine learning: the average of the last 3 months).

5Model versions and promotion

Each training run is one model with its own model ID (for example CFF_202610_20261107T1000: cut-off month and training time), recorded in Dataiku's Experiment Tracking and deployed as a new version of the saved model cash_forecast. The production model is the active version; the nightly forecast always uses it.

flowchart LR
  T[Train and test a new model with the chosen forecaster] --> X[(Experiment Tracking: model ID, forecaster, settings, test scores)]
  X --> V[(New version of cash_forecast, not active)]
  V --> CC{Champion / challenger: same last 6 months, promotion rules}
  P[(Active version: production)] --> CC
  CC -- passes --> PR[Activate the new version]
  CC -- fails --> K[Keep the active version]
  PR --> AV[(Active version)]
  K --> AV
  AV -. read on its own schedule .-> N[Nightly batch: forecast with the active version]

The promotion rules are project variables: they change without touching the code.

Rule (project variable)DefaultThe new model is promoted only if
promotion_min_coverage, promotion_max_coverage0.70, 0.90its P10–P90 coverage is in this range (80% is the aim)
promotion_beat_simple_guesstrueits EV error is lower than the simple guess's (the same as the month before)
promotion_min_gain0.0its EV error is lower than the production model's by more than this share (0.02 = 2%); a tie keeps production
  • With no production model yet, the first model is promoted (the forecast needs one), with a warning if it fails the rules.
  • Every decision, its reason and the rules used go to promotion_log.
  • Rollback: activate an earlier version of cash_forecast and run the nightly batch.

7Testing

Every model is tested the same way: trained without the last 6 months, it forecasts each of them from the data known the month before, and we compare with what really happened.

CheckWhat it tells usGood result
EV error (WAPE)Total of |actual − EV| divided by total of |actual|As low as possible, and better than the simple guess (the same as the month before)
P10–P90 coverageShare of actual months that fall between P10 and P90About 80% (about 10% below P10, about 10% above P90)

Results are shown per months ahead, for the TOTAL rows and the category rows; promotion uses all rows together. In the sandbox the data is simulated: the scores show the pipeline works, not which model is better.

8What gets built in Dataiku

A setup notebook builds the project in a Dataiku project (a few minutes with the small sample data, including the first model). It needs no admin right, and it can be run again in the same project: what exists is kept and the recipes' code is updated. Every dataset is a CSV file (compressed for the big ones, daily_flows and final_forecast). Two independent scenarios run it: Nightly batch after each warehouse load (never trains), and Retrain, test and promote (monthly, or when needed; never forecasts). A third one, Full rebuild of the daily flows, is run by hand. The zones only meet through three interfaces: 1. the data (daily_flows, clients), 2. the forecaster (lab → training), 3. the active version of the saved model (training → inference, the only thing inference reads from training).

9Inference log

The recipe final_forecast is built for the bank's ~420,000 clients: it forecasts a chunk of clients at a time (project variable inference_clients_per_chunk, 5,000 by default), so memory holds one chunk whatever the number of clients. Every run adds one row to inference_log (in the Inference zone) and keeps the forecast as it was made, compressed, in the folder forecast_archive.

ColumnWhat it says

Scenario run history shows every run and its failures; in production, add a reporter (email, Slack) to the scenarios. Model monitoring (drift, accuracy against actuals) is left out for now.

10Decisions and open points

Agreed

  • Input: the daily flows per client, day and category, over each client's whole history. No monthly table in between.
  • Output: per client, category and TOTAL, one value per month for each of the next 3 months, as P10, EV and P90.
  • Small models only, no deep learning. A placeholder (quantile_boosting: 3 models for EV, P10 and P90, shared by all categories) until the data scientist's models are ready.
  • Each training run is tracked with a model ID and deployed as a version of cash_forecast; it is activated only if it passes the promotion rules (project variables); the nightly batch uses the active version.
  • The warehouse is only read, never written to: Dataiku does all the prep and the modelling. Everything the project writes is a CSV file.
  • At least 12 months of history to forecast a client; otherwise flagged. Test on the last 6 months.

To check

  • Scale: staging reads only the new days and inference works in chunks of clients, tested here with 420,000 fake clients (notebook inference_load_test.ipynb). Run the same test on the bank's server, as its benchmark, to set the chunk size; partitions or parallel chunks only if it is still too slow.
  • The real transaction type codes (TRNS_TYP) and the categories they map to, to replace the mock list.
  • The first read of the whole of FCT_STATEMENT_ENTRY (and each Full rebuild): check how long it takes on the real table. Training still reads all clients at once: train on a sample of clients when that gets too heavy.
  • Code env: a Python code env with scikit-learn and mlflow 2.22.0 (Python 3.9) or 3.10.1 (Python 3.10 or later). We cannot create one: a Dataiku admin creates it once.
  • The codes the project relies on (status values, retail line of business, commercial registration, sole proprietor legal entities): confirm them on business clients. If they differ, only warehouse.py changes.
